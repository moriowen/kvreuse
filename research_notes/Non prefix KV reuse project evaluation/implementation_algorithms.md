## Q1. RoPE math for Mistral, re-rotation by delta, precision, HF cos/sin, other RoPE variants

### Takeaway
Mistral v0.3 uses plain (unscaled) RoPE with theta = 1e6, head_dim 128, HF's "rotate_half" (NeoX, split-halves) pairing, so re-rotating a stored post-RoPE key by delta = new_pos − old_pos with the same cos/sin formula is exact in real arithmetic. The rounding error is about `pos × inv_freq × 6e-8` radians in fp32, so the E0 fp32 tolerance has to be set from position, not as a blanket 1e-6. Llama-3-style scaling keeps delta rotation exact. YaRN (which scales cos/sin by a factor) and dynamic NTK (which changes frequencies with sequence length) do not.

### Cited Findings
- **Config facts [doc]:** Mistral-7B-Instruct-v0.3 `config.json`: `num_attention_heads: 32`, `num_key_value_heads: 8`, `hidden_size: 4096` (→ head_dim 128), `num_hidden_layers: 32`, `rope_theta: 1000000.0`, `sliding_window: null`, `max_position_embeddings: 32768`, `vocab_size: 32768`, `bos_token_id: 1`, `eos_token_id: 2`, `torch_dtype: bfloat16`, no `rope_scaling` key. — [config.json](https://huggingface.co/mistralai/Mistral-7B-Instruct-v0.3/blob/main/config.json)
- **rotate_half [code]:** `x1 = x[..., :d/2]; x2 = x[..., d/2:]; return cat((-x2, x1))` (modeling_mistral.py L50-55). Dimension i is paired with i+64, not with the adjacent 2i/2i+1 (interleaved) pairing in the RoFormer paper. — [modeling_mistral.py](https://github.com/huggingface/transformers/blob/main/src/transformers/models/mistral/modeling_mistral.py)
- **apply_rotary_pos_emb [code]:** `cos = cos.unsqueeze(1); sin = sin.unsqueeze(1); q_embed = q*cos + rotate_half(q)*sin; k_embed = k*cos + rotate_half(k)*sin` (L58-80). Tensors are `[batch, heads, seq, head_dim]` and cos/sin are `[batch, seq, head_dim]`, so `unsqueeze_dim=1` broadcasts over heads. — [modeling_mistral.py](https://github.com/huggingface/transformers/blob/main/src/transformers/models/mistral/modeling_mistral.py)
- **inv_freq [code]:** `compute_default_rope_parameters`: `base = config.rope_parameters["rope_theta"]`; `inv_freq = 1.0 / (base ** (torch.arange(0, dim, 2, dtype=torch.float) / dim))`; `attention_factor = 1.0` (L279-295). On current main, theta is read from `config.rope_parameters`. Older 4.4x releases used `config.rope_theta` directly. — [modeling_mistral.py](https://github.com/huggingface/transformers/blob/main/src/transformers/models/mistral/modeling_mistral.py)
- **cos/sin computation [code]:** `MistralRotaryEmbedding.forward`: `freqs = position_ids[..., None].float() * inv_freq.float()`; `emb = cat((freqs, freqs), -1)`; `cos = emb.cos() * attention_scaling`; `sin = emb.sin() * attention_scaling`; `return cos.to(x.dtype), sin.to(x.dtype)` (L297-305). The angles are fp32, but cos/sin are **cast to the model dtype (bf16) before they multiply the keys**. `MistralModel.forward` computes `position_embeddings = self.rotary_emb(hidden_states, position_ids)` once and passes it to every layer (L363-369). — [modeling_mistral.py](https://github.com/huggingface/transformers/blob/main/src/transformers/models/mistral/modeling_mistral.py)
- **K is stored post-RoPE [code]:** `MistralAttention.forward` applies RoPE and then calls `past_key_values.update(key_states, value_states, self.layer_idx)` (L153-157). Anything you read out of a `DynamicCache` is already post-RoPE, in model dtype, with shape `[B, 8, T, 128]`. — [modeling_mistral.py](https://github.com/huggingface/transformers/blob/main/src/transformers/models/mistral/modeling_mistral.py)
- **Relative-position property [doc]:** CacheBlend Appendix A (Proposition A.2) proves that the RoPE attention score depends only on relative distance, and §4 states that the position correction "is done simply by multiplying the K vector by a rotation matrix". — [CacheBlend arXiv 2405.16444](https://arxiv.org/html/2405.16444)
- **CacheBlend stores pre-RoPE K and rotates to absolute positions instead of applying a delta [code]:** In `llama.py` `LlamaAttention.forward`, `self.hack_kv = [k.clone(), v.clone()]` runs **before** `q, k = self.rotary_emb(positions, q, k)`. At blend time the old K is rotated once with `self.rotary_emb(cache_fuse_metadata['org_pos'], fake_q, old_kv[0])`, where `org_pos` is the full prompt's positions and `fake_q = torch.rand_like(q)` is a throwaway (lines ~171-183, marked `# HACK(Jiayi): Rotate the old K`). EPIC's fork does the same (`epic/vllm/model_executor/models/llama.py` L207-226). — [CacheBlend llama.py](https://github.com/YaoJiayi/CacheBlend/blob/main/vllm_blend/vllm/model_executor/models/llama.py); [EPIC llama.py](https://github.com/DerekHJH/epic/blob/main/vllm/model_executor/models/llama.py)
- **YaRN scales cos/sin [code]:** `_compute_yarn_parameters` sets `attention_factor = get_mscale(factor)` (modeling_rope_utils.py ~L439), and the rotary forward multiplies cos and sin by it. Dynamic NTK recomputes `base = base * ((factor*seq_len/max_pos) - (factor-1)) ** (dim/(dim-2))` (L340), so the frequencies depend on the current sequence length, and `dynamic_rope_update` (L34-118) refreshes `inv_freq` when `max(position_ids)+1` grows. Linear scaling and the "proportional" type return `attention_factor = 1.0` (L181, L244). — [modeling_rope_utils.py](https://github.com/huggingface/transformers/blob/main/src/transformers/modeling_rope_utils.py)

### Inferences
- **Why delta works [inference, standard math]:** Each rotate_half pair (i, i+64) is a 2-D rotation by θ_i·p. 2-D rotations compose additively, R(θa)R(θb) = R(θ(a+b)), so `rope(k_raw, p_new) = rope(rope(k_raw, p_old), p_new − p_old)`. Re-rotating means calling `apply_rotary_pos_emb` on the *cached* K with cos/sin built from `delta`. Use the same pairing convention (rotate_half). The interleaved RoFormer formula would rotate the wrong pairs and fail silently at layer 0.
- **Re-rotation recipe consistent with the assumed decision [inference]:**
  ```python
  inv_freq = model.model.rotary_emb.inv_freq.float()            # [64]
  delta = (new_start - old_start)                                # int, may be negative
  ang = delta * inv_freq                                         # fp32 (or fp64 for tests)
  emb = torch.cat([ang, ang], -1)                                # [128]
  cos, sin = emb.cos(), emb.sin()                                # same for every token in the chunk
  k32 = k_cached.float()                                         # [B, 8, T, 128]
  k_new = (k32 * cos + rotate_half(k32) * sin).to(torch.bfloat16)
  ```
  Every token in a chunk shifts by the same delta, so one cos/sin vector broadcasts over the chunk. That is cheaper than HF's per-token table. V never needs rotation.
- **Size of precision error [inference]:** inv_freq[0] = 1.0, so at absolute position p the highest-frequency angle is p radians, and its fp32 rounding error is about ulp(p) ≈ p·6e-8 (≈1e-3 rad at p = 16K). HF computes `fl(p·f)` while the delta path computes `fl(p_old·f) + fl(Δ·f)`. These differ by a few ulps of the angle, so even in fp32 the layer-0 keys will not agree to 1e-6 at large positions. The error is largest in the first (highest-frequency) dims. Two ways to handle it in E0: (a) build **both** the reference and the test from fp64 angles, done outside HF, and then use a tight tolerance; or (b) keep HF's fp32 reference and scale the tolerance as `atol ≈ c·p·6e-8·|k|`. For theta = 1e6 the low-frequency dims have tiny angles and are essentially exact.
- **bf16 [inference]:** bf16 has an 8-bit mantissa (relative step ~4e-3), and HF casts cos/sin to bf16 *before* the multiply, so HF's own bf16 prefill keys carry roughly 1e-2 relative noise. A bf16 cache that is correct but re-rotated in fp32 will **not** match HF bf16 bit-for-bit, and may sit closer to the true value than the reference does. That is why the bf16 E0 run measures a noise floor rather than passing an exactness check. Each re-rotation adds one bf16 rounding of K. Never re-rotate a chunk twice (old→mid→new). Always rotate from the stored canonical position, which is what "cast to bf16 once" protects.
- **Canonical storage position [inference]:** Store each chunk at a canonical start (for example, position of the first chunk token = its offset after the header/BOS it was prefilled with). Then delta = target_start − canonical_start. The alternative is CacheBlend's design (store pre-RoPE K, rotate once to absolute positions), which needs no delta and has no compounding error, but HF's cache only gives you post-RoPE K. Getting pre-RoPE K would require a forward hook on `k_proj`, or un-rotating with −p_old (exact up to rounding).
- **Other models [inference from code]:** Llama-3 `rope_type="llama3"` only rescales `inv_freq` per frequency band, with attention_factor 1. Rotation stays linear in position, so delta rotation is exact **as long as you use the model's own `rotary_emb.inv_freq`, not a hand-recomputed `theta**(-2i/d)`**. Qwen2/2.5/3 use the same rotate_half convention with default RoPE (Qwen3 adds q/k RMSNorm *before* RoPE, which does not interact with re-rotation). YaRN: build the delta cos/sin **without** attention_factor, or the scale compounds (K ends up scaled by mscale²). Dynamic NTK: frequencies change with total length, so a cached chunk is rotated with the wrong base whenever the assembled prompt crosses `original_max_position_embeddings`. Delta rotation cannot fix that. Store pre-RoPE K or disable dynamic scaling. Mistral v0.3 has none of these.

## Q2. Writing a per-layer forward in current Transformers: layers, position_ids, masks for a non-contiguous query set, cache handling, attention backends; how CacheBlend and EPIC do it

### Takeaway
Drive `model.model.layers[i]` yourself, but call the attention sub-module with hand-built tensors rather than through `DynamicCache`. Give each selected token its true `position_ids`, build an **explicit 4-D boolean mask** `mask[q, kv] = kv_pos <= q_pos[q]`, and use `attn_implementation="sdpa"` or `"eager"`. Never pass `attention_mask=None` for a subset query (HF then sets `is_causal=True`, which is wrong), and do not use FlashAttention-2 (it cannot take an arbitrary mask). CacheBlend's reference code uses a bottom-right triangular mask that is *not* exact for scattered tokens. EPIC's code builds the exact row-sliced mask.

### Cited Findings
- **Decoder layer API [code]:** `MistralDecoderLayer.forward(hidden_states, attention_mask=None, position_ids=None, past_key_values=None, use_cache=False, position_embeddings=None, **kwargs)` (L210-240). `MistralModel.forward` runs `embed_tokens`, then `create_causal_mask` (or `create_sliding_window_causal_mask` if `sliding_window` is not None), then `rotary_emb` once, then the loop over `self.layers`, then `self.norm` (L329-381). — [modeling_mistral.py](https://github.com/huggingface/transformers/blob/main/src/transformers/models/mistral/modeling_mistral.py)
- **Attention internals [code]:** q/k/v projections, `.view(*input_shape, -1, 128).transpose(1,2)`, RoPE, optional `past_key_values.update`, then `ALL_ATTENTION_FUNCTIONS.get_interface(config._attn_implementation, eager_attention_forward)` called with `(self, q, k, v, attention_mask, scaling=head_dim**-0.5, sliding_window=...)`, then `o_proj` (L138-178). Eager repeats KV for GQA via `repeat_kv` (n_rep = 4), adds the mask additively, and runs softmax in fp32 (L95-118). — [modeling_mistral.py](https://github.com/huggingface/transformers/blob/main/src/transformers/models/mistral/modeling_mistral.py)
- **SDPA `is_causal` trap [code]:** `sdpa_attention_forward` sets `is_causal = q_length > 1 and attention_mask is None and is_causal` (L136). If `is_causal and attention_mask is None and kv_length > q_length`, it **crops K/V to the first q_length tokens** (L157-162), because "sdpa's `is_causal` mask alignment is upper-left" (L151). GQA goes through `enable_gqa=True` when supported, otherwise `repeat_kv` (L108-114). — [sdpa_attention.py](https://github.com/huggingface/transformers/blob/main/src/transformers/integrations/sdpa_attention.py)
- **HF mask builders assume a contiguous query block [code]:** `sdpa_mask` builds `q_arange = torch.arange(q_length) + q_offset` (L512) and applies `causal_mask_function: kv_idx <= q_idx` (L77-81), so the query positions must be consecutive. `_ignore_causal_mask_sdpa` may return `None` (no mask) for an empty-cache prefill (L236-283). — [masking_utils.py](https://github.com/huggingface/transformers/blob/main/src/transformers/masking_utils.py)
- **CacheBlend control flow [code]:** `cache_fuse_metadata = {"check_layers":[1], "recomp_ratio":0.16, ...}`. Per layer, status 0 = full prefill (layer 0), status 1 = the check layer (index 1), status 2 = after the check. After the check layer, `positions = positions[imp_indices]`, and `residual = residual[imp_indices]` in the decoder layer, so only selected tokens' hidden states flow to later layers. — [CacheBlend llama.py](https://github.com/YaoJiayi/CacheBlend/blob/main/vllm_blend/vllm/model_executor/models/llama.py)
- **CacheBlend KV write-back [code]:** In status 2, `key_old[imp_indices] = key; value_old[imp_indices] = value; key = key_old; value = value_old`, then attention runs with the selected queries over the full merged K/V. The attention bias is `LowerTriangularFromBottomRightMask()`, and the exact `_make_partial_bias_gqa` call is commented out (xformers.py L219-221, L240-245, L426-436). — [CacheBlend xformers.py](https://github.com/YaoJiayi/CacheBlend/blob/main/vllm_blend/vllm/attention/backends/xformers.py)
- **EPIC's exact mask [code]:** `_make_partial_bias_mha`/`_gqa` build the full `triu(ones(L,L), 1) * finfo.min` causal mask and **slice its rows** with `attn_mask[:, :, imp_indices]`. It is used for both the CacheBlend path and the kvlink (LegoLink) path. For kvlink, the hidden states and positions are sliced to `imp_indices` **before layer 0** (`hidden_states = hidden_states[imp_indices]`), so the selected tokens are recomputed at every layer including 0. — [EPIC xformers.py](https://github.com/DerekHJH/epic/blob/main/vllm/attention/backends/xformers.py) L506-551, L905-925; [EPIC llama.py](https://github.com/DerekHJH/epic/blob/main/vllm/model_executor/models/llama.py) L433-443
- **Reference chunk assembly [code]:** CacheBlend `example/blend.py` (Mistral-7B-Instruct-**v0.2**): `doc_chunk_ids = [tokenizer.encode(doc)[1:] ...]` strips BOS. The first "chunk" is `s_start_full = [733, 4138, 28793]` (`[INST]`) plus BOS. Each chunk's KV is collected by running it alone, and slices are concatenated on dim 0. The query chunk is `q_ids + s_end` with `s_end = [733, 28748, 16289, 28793]` (`[/INST]`). The final prompt is passed as text with `max_tokens=10`. — [CacheBlend blend.py](https://github.com/YaoJiayi/CacheBlend/blob/main/example/blend.py)
- **LMCache / issues:** The proposal records that LMCache's blending example is reported out of date for recent vLLM (issue #4476) and that the newer blend mode has no multi-process vLLM client (issue #5101). I did not re-read LMCache's blend modules. — proposal §1 (local file)

### Inferences
- **Recommended C2 structure [inference]:** Skip `DynamicCache` for the reuse path. Keep a list `kv[l] = (K[l], V[l])` of plain tensors `[1, 8, N, 128]` (bf16) for the assembled prompt (system + re-rotated chunks + question). Per layer `l` with recompute set `S` (sorted absolute indices, always including every question token):
  ```python
  layer = model.model.layers[l]; attn = layer.self_attn
  h_S = hidden[:, S]                                   # hidden states of S only
  x = layer.input_layernorm(h_S)
  q = attn.q_proj(x).view(1, s, 32, 128).transpose(1, 2)
  k = attn.k_proj(x).view(1, s, 8, 128).transpose(1, 2)
  v = attn.v_proj(x).view(1, s, 8, 128).transpose(1, 2)
  cos, sin = model.model.rotary_emb(x, position_ids=pos[S][None])   # true absolute positions
  q, k = apply_rotary_pos_emb(q, k, cos, sin)
  K, V = kv[l]; K[:, :, S] = k; V[:, :, S] = v          # write fresh KV back (method 4: offset others here)
  mask = (pos[None, :] <= pos[S][:, None])[None, None]  # [1,1,s,N] bool, True = attend
  out = F.scaled_dot_product_attention(q, K, V, attn_mask=mask, enable_gqa=True, scale=attn.scaling)
  h_S = h_S + attn.o_proj(out.transpose(1, 2).reshape(1, s, -1))
  h_S = h_S + layer.mlp(layer.post_attention_layernorm(h_S))
  hidden[:, S] = h_S
  ```
  This mirrors the HF module but lets you control the mask. Calling `layer(...)` with a custom 4-D mask and a pre-filled cache also works in principle, but `DynamicCache.update` *appends*, while you need *scatter* writes, so plain tensors are simpler. **Write back before attention** (as CacheBlend's status-2 code does), so recomputed tokens see each other's fresh KV.
- **Hidden states for S across layers [inference]:** A token in S at layer l needs its *fresh* hidden state from layer l−1. That only exists if the token was in S at every earlier layer since the start (layer 0 or the selection layer). So S must be **non-increasing** from the first layer at which it is defined: S_l ⊆ S_{l−1}. CacheBlend's gradual filtering satisfies this, and so do EPIC/AgentKVShift with a fixed set. A token cannot join S at layer 10 unless you keep full hidden states for all tokens, which defeats the savings.
- **Selection layer [inference]:** For CacheBlend and AgentKVShift the selection needs fresh K/V for **all** chunk tokens at layer 1 (0-indexed). That means running layer 0 fully (all tokens, which is also exact by the layer-0 argument) and computing at least the q/k/v projections at layer 1 for all tokens. The CacheBlend code computes qkv for all tokens at layer 1, attends with **fresh full K/V** (`key_old` not substituted, L232-238), and runs attention + MLP only for the selected queries.
- **Masks [inference]:** For SDPA, a boolean mask with True = attend, or an additive float mask in the query dtype. Make sure no row is fully masked: every query attends at least to itself and BOS, so this is fine. FlashAttention-2 in HF supports only causal/varlen masks, so non-contiguous queries are not expressible. Use SDPA (the math or mem-efficient kernel is chosen automatically when a mask is given) or eager. For the full-prefill reference, run the stock `model(input_ids)` with the same `attn_implementation` you use in C2, so kernel differences don't count as reuse error.
- **CacheBlend's mask is approximate [inference from code]:** `LowerTriangularFromBottomRightMask` with q_len = s and kv_len = N lets query row i see keys 0..N−s+i. For scattered selected tokens that is not each token's true causal horizon (early selected tokens can see future keys). Its query suffix is the last rows, and those are handled correctly. Implement the exact mask (EPIC style). If you compare to CacheBlend's published numbers, mention this difference.
- **Sliding window:** v0.3 has `sliding_window: null` [doc, config], so there is no windowing in the custom mask. Mistral v0.1 had a 4096 window; ignore it.

## Q3. Exact algorithms of the four correction methods and how each counts its recompute budget

### Takeaway
The papers and the reference code differ in ways that matter for an apples-to-apples comparison. CacheBlend's paper describes gradual filtering on KV/attention deviation, but its code does a single top-k at layer 1 on **V only**, with ratio 0.16. EPIC's code recomputes the first k tokens of each retrieved chunk at **every layer from layer 0**, plus the whole question, with k ∈ {1…64}. AgentKVShift selects separate top-b K and V probe sets per chunk at check layer ℓc = 1 and adds a weighted mean offset (w = min(d, 1)) to non-probes at every layer. None of them charges the full-compute selection layer against the budget. Count that layer yourself.

### Cited Findings

**Method 1, re-positioning only (Naive)**
- In EPIC's code, `naive` sets `kvlink = [start_offset[-1] - 1]`, so only the **last prompt token** is recomputed. — [EPIC e2e/main.py](https://github.com/DerekHJH/epic/blob/main/benchmarks_ours/evals/e2e/main.py) L192-195
- EPIC's paper: Naive "reuses cached KV vectors directly with zero recomputation overhead but severe accuracy degradation". — [EPIC arXiv 2410.15332](https://arxiv.org/html/2410.15332)

**Method 2, EPIC / LegoLink**
- "LegoLink recomputes each chunk's first k tokens (except the first chunk)". Variants evaluated include LegoLink-2/-16, and LegoLink-0 "prepends four dummy tokens (e.g., begin-of-sentence tokens) to each immutable chunk during compilation, then discards their corresponding KV vectors". The paper explains the attention sink: "The initial tokens of each chunk disproportionately absorb attention, impeding subsequent tokens from attending to relevant context". Complexity is O(kN) vs CacheBlend's O(15% N²) (as summarized by fetch). — [EPIC arXiv 2410.15332](https://arxiv.org/html/2410.15332)
- **Code [code]:** Chunks = `[system_token_ids (chat template)] + [tokenizer.encode(mod) for mod in mods] + [encode(question) + eos]`. Each chunk is prefilled alone **with its own BOS kept** ("Include all tokenizer.bos_token_id"). `kvlink-k` recomputes `range(start, start+k)` for every *module* chunk (index 1 … n−2) and **the entire last chunk** (the question). The "first chunk" that is skipped is the system prompt, not the first retrieved document. Approaches swept: `kvlink-{64,32,16,8,4,2,1}` and `cacheblend-{20,15,10,5,1}`. — [EPIC e2e/main.py](https://github.com/DerekHJH/epic/blob/main/benchmarks_ours/evals/e2e/main.py) L133-235
- "AttnLink": no variant by that name showed up in the arXiv HTML I fetched or in the code (the code calls it `kvlink`). The variants listed are Naive, Fully Recompute, CacheBlend, LegoLink(-k), and LegoLink-0. — [EPIC arXiv 2410.15332](https://arxiv.org/html/2410.15332)

**Method 3, CacheBlend**
- **Paper [doc]:** KV deviation is "the absolute difference between KV_i[j] and KV_i^full[j]". Gradual filtering: pick r₁% (> r) tokens at the first layer by deviation, recompute those on the next layer, keep r₂% (< r₁) "that have the highest token-wise attention deviation", and so on. "If we recompute r% of tokens per layer, the total compute overhead will be r% of full prefill." 10-20% suffices empirically, and the loading controller uses r* = 15% as a floor. — [CacheBlend arXiv 2405.16444](https://arxiv.org/html/2405.16444) §4.2-4.3, §5
- **Code [code]:** `check_layers=[1]`, `recomp_ratio=0.16`. At the check layer: `topk_num = int((total_len - last_len) * recomp_ratio)`; `temp_diff = torch.sum((value[:-last_len] - value_old[:-last_len])**2, dim=[1,2])`, i.e. **squared L2 of V only, summed over all 8 KV heads × 128 dims**, with no K and no attention deviation. `top_indices = sort(topk(temp_diff))`, then `cat` with the suffix indices. There is **one** selection and no gradual narrowing in later layers. — [CacheBlend xformers.py](https://github.com/YaoJiayi/CacheBlend/blob/main/vllm_blend/vllm/attention/backends/xformers.py) L204-217
- **Code bug [code]:** `blend.py` sets `last_len = len([q_ids+s_end])`, the length of a one-element list, so `last_len = 1`. Only the final token is forced in as "suffix"; the other question tokens must win the top-k (comment: `#TODO (Jiayi): fix last len`). EPIC's fork hard-codes the same (`value[:-1]`, appends `query.shape[0]-1`). — [CacheBlend blend.py](https://github.com/YaoJiayi/CacheBlend/blob/main/example/blend.py); [EPIC xformers.py](https://github.com/DerekHJH/epic/blob/main/vllm/attention/backends/xformers.py) L531-535
- The selection ratio applies to all non-suffix tokens **including the system prompt/first chunk**, not per chunk. — same files

**Method 4, AgentKVShift (Algorithm 1, §3.3)**
- Algorithm 1 as fetched: (3) per chunk C, compute d_K,j and d_V,j at ℓc and "select top-b probe sets S_C^K, S_C^V, set weights w_K,j, w_V,j". (4-5) for ℓ = 1..L, "Recompute fresh KV for S_C^K ∪ S_C^V at layer ℓ". (6) μ̂_K,C^ℓ ← (1/b) Σ_{j∈S_C^K} (K_j,fresh^ℓ − K_j,reuse^ℓ), with μ̂_V analogous. (8) K_j,corr^ℓ ← K_j,fresh^ℓ if j ∈ S_C^K, else K_j,reuse^ℓ + w_K,j μ̂_K,C^ℓ. (9) same for V with S_C^V. — [AgentKVShift arXiv 2607.21604](https://arxiv.org/html/2607.21604) Algorithm 1
- d_K,j = ‖K_j,fresh^ℓc − K_j,reuse^ℓc‖₂ (likewise V). ℓc = 1 ("the first transformer layer"). b = ⌈r·n⌉ per chunk with n = chunk length. w_K,j = min(d_K,j, 1) and w_V,j = min(d_V,j, 1), with d unnormalized. Probe tokens use their fresh states directly. r is swept over {0.05, 0.10, …, 0.95}. Baselines: CacheBlend ("selectively recomputes high-deviation tokens identified at a check layer") and ProphetKV ("replaces divergence-based selection with query-driven criterion") at the same r. — [AgentKVShift arXiv 2607.21604](https://arxiv.org/html/2607.21604) §3.3, §4.1, §4.3
- Mistral-7B LoCoMo with LiCoMemory, r = 0.1: F1 0.491 vs full recompute 0.509 (Table 1). No code URL in the paper. — [AgentKVShift arXiv 2607.21604](https://arxiv.org/html/2607.21604)
- Appendix E limitation (per the concept guide's reading): K and V residuals behave differently, and the offset fits K better. — local `concept-guide.md`

**ProphetKV:** only described in AgentKVShift as a query-driven selection baseline. I did not read its paper.

### Inferences
- **Budget accounting differs by method [inference from code]:**
  - CacheBlend code: layer 0 is 100% computed, and layer 1 computes qkv for 100% of tokens plus attention/MLP for the selected ones. Layers 2-31 compute ~16% + 1 token. Its "16%" therefore costs about `(1 + 1·qkv_frac + 30·0.16)/32` of full prefill in linear FLOPs, roughly 18-20% rather than 16%.
  - EPIC: k tokens per chunk × all 32 layers, plus the question. No selection layer.
  - AgentKVShift: by Algorithm 1 the probes are recomputed at ℓ = 1..L. The divergence at ℓc needs fresh K/V for **all** chunk tokens at ℓc, which requires their fresh layer-(ℓc−1) hidden states. If ℓc means 0-indexed layer 1, layer 0 must be run in full. If it means the very first layer (HF index 0), the divergence is **identically zero** after exact re-rotation (layer-0 KV depends only on token and position), and selection degenerates. **So ℓc must be HF layer index 1, preceded by a full layer 0.** The paper doesn't say whether that full layer is counted in r. One summary pass claimed it is "included", but I could not verify that wording. Treat it as undocumented.
  - The proposal already commits to "Recomputed tokens are counted the same way for every method, including tokens touched at a selection layer." Concretely, report **budget = Σ_layers |S_l| / (32 · N_reusable)**, with the question tokens excluded from both numerator and denominator (they are always fresh), and charge full layers as |S_l| = N. Also report FLOPs (Q5).
- **Two probe sets [inference]:** S^K and S^V are selected separately, so |S^K ∪ S^V| ranges from b to 2b, and the true recompute is up to 2·r. Fix this in accounting: either cap the union at b, or count the union.
- **Offset and RoPE [inference, not in the paper]:** With post-RoPE storage, the residual of token j is rotated by its own angle. Averaging post-RoPE residuals across positions partially cancels the high-frequency dims, and the offset is then added in the wrong rotation frame for each token. Pre-RoPE averaging (un-rotate each residual by −p_j, average, re-rotate by +p_j per token) is the frame-consistent variant. The paper doesn't say which frame it uses. Make it an ablation, and default to the post-RoPE version as literally written.
- **Offset is elementwise [inference]:** The mean over tokens is per-dimension anyway, so "per head vs global" matters only for d_j (one scalar per token over 8×128 dims) and hence w_j. Since w = min(d, 1) with unnormalized d, most tokens in deep layers will have d ≫ 1 and w = 1. Log the w distribution, because the cap at 1 may be effectively always active.
- **When "fresh" K is defined [inference]:** In Algorithm 1, K_reuse^ℓ for non-probes is the **stored** chunk KV (re-rotated), not something recomputed. Only probes run through layers ≥ 1. At layer ℓ the non-probes keep stale KV + offset. Their hidden states are never computed, which is consistent with the S_l ⊆ S_{l−1} constraint in Q2.
- **Question tokens [inference]:** Every method should recompute all question tokens at all layers, outside the budget. The proposal states the question "is always computed fresh". CacheBlend's code only guarantees the last token (bug above). Don't replicate that.
- **EPIC k for 256-token chunks [inference]:** The paper's 16-32 is for LongBench passages. With ~256-token chunks, k = 16 is 6% and k = 32 is 12.5% of each chunk, plus a header. Since the session-date header sits at the start of every chunk, EPIC's first-k tokens will be mostly header. Sweep k ∈ {4, 8, 16, 32, 64} to trace the curve.

- AgentKVShift: zero- vs one-indexing of ℓc, the RoPE frame for offsets, whether the selection layer is charged to r, and how the question/system prompt are treated are all unstated in the parts fetched. No code was released.
- CacheClip (2510.10129) and APE were not read (tool budget). They are adjacent methods, not one of the four.

## Q4. Pitfalls: tokenizer boundaries, chat template, attention sink, nondeterminism, 100% recompute = full prefill, fair timing, FLOPs

### Takeaway
Most E0 failures come from token-boundary mismatches (BOS/leading-space), the v0.3 chat template putting the "system" text inside the *last* `[INST]`, and SDPA's implicit `is_causal`. Time with `torch.cuda.Event` after warmup and include the selection layer and the re-rotation in the timed region.

### Cited Findings
- **Mistral v0.3 chat template [code]:** If `messages[0]` is system, it is held back and emitted as `"[INST] " + system_message + "\n\n" + message["content"] + "[/INST]"` **only on the last user turn** (`loop.last`). Prompts start with `bos_token`, and assistant turns are `" " + content|trim + eos_token`. Roles must alternate user/assistant. Tokenizer config: `add_bos_token: True`, `add_eos_token: False`, `legacy: False`, `add_prefix_space: True`, class `LlamaTokenizer`. — [tokenizer_config.json](https://huggingface.co/mistralai/Mistral-7B-Instruct-v0.3/blob/main/tokenizer_config.json)
- **Reference implementations strip BOS per chunk:** CacheBlend uses `tokenizer.encode(doc)[1:]`. EPIC keeps every chunk's BOS (comment "Include all tokenizer.bos_token_id"), and its LegoLink-0 variant intentionally prepends sink tokens and discards their KV. — [CacheBlend blend.py](https://github.com/YaoJiayi/CacheBlend/blob/main/example/blend.py); [EPIC e2e/main.py](https://github.com/DerekHJH/epic/blob/main/benchmarks_ours/evals/e2e/main.py); [EPIC arXiv](https://arxiv.org/html/2410.15332)
- **Attention sink [doc]:** chunks compiled with positions from 0 make their initial tokens absorb attention, which is wrong mid-prompt. — [EPIC arXiv](https://arxiv.org/html/2410.15332)
- **SDPA implicit causal / cropping:** see Q2. — [sdpa_attention.py](https://github.com/huggingface/transformers/blob/main/src/transformers/integrations/sdpa_attention.py) L136, L151-162

### Inferences
- **Tokenizer boundaries [inference]:** With `add_prefix_space: True` / SentencePiece, `encode(A) + encode(B)` ≠ `encode(A + B)` at the join: a leading "▁" may appear on B's first token, and A's last token may merge differently. Because the proposal assembles by **token-ID concatenation** of once-tokenized chunks, the "full prefill" reference must use **exactly the same concatenated IDs**, never re-tokenized text. CacheBlend's `blend.py` decodes to text and re-encodes the final prompt, which reintroduces this risk. Encode each chunk with `add_special_tokens=False` and make every chunk start with a fixed separator such as `"\n\n"` or the header, so the leading-space behavior is the same in every context. Assert `ids == concat(ids_i)` once per prompt.
- **Prompt layout under v0.3 [inference]:** The template has no standalone system turn, so build the single-turn prompt by hand as `[BOS] [INST] ␣<system text>\n\n<chunk_1>…<chunk_k>\n\n<question + instruction>[/INST]`. Treat `[BOS][INST] system\n\n` as the never-reused prefix (always computed or prefix-cached), then the reused chunks, then the fresh question + `[/INST]`. Verify against `apply_chat_template` once (system+user), so the boundaries match the model's training format.
- **How a chunk is prefilled alone [inference]:** Prefill each chunk as `[BOS] [INST] ␣<chunk ids>` (or BOS + chunk) and keep only the chunk's KV slice. That gives a realistic sink and canonical positions. Prefilling without BOS makes the chunk's own first token the sink, which is exactly the EPIC failure mode, and makes Method 1 look worse than necessary. Pick one convention for all methods, record it, and consider it an ablation.
- **100% recompute = full prefill [inference]:** If S = all tokens at every layer and the mask is exact, the custom loop computes the same function as `model(ids)`. The reused KV is overwritten at every layer before it is read, because write-back happens before attention. A mismatch beyond kernel noise means a bug: a wrong mask, wrong positions, a missing write-back, the final norm/lm_head not applied, or a different attn backend. In fp32 with the same backend, expect agreement to roughly 1e-5 relative in logits. In bf16, compare argmax/top-k and KL rather than exact values.
- **Nondeterminism [inference]:** SDPA/cuBLAS kernel choice depends on shapes. Masked SDPA with s ≠ N may dispatch to a different kernel than the full-prefill path. Set `torch.backends.cuda.matmul.allow_tf32 = False` for fp32 E0 (TF32 default-on for convs and possibly for matmul would wreck tight tolerances), and use `torch.use_deterministic_algorithms(True)` plus `CUBLAS_WORKSPACE_CONFIG=:4096:8` for E0 only.
- **Fair timing [inference, standard practice]:** Warm up 3-5 iterations per shape. Bracket with `torch.cuda.Event(enable_timing=True)`, call `record()` before and after, `torch.cuda.synchronize()`, then `elapsed_time`. Report the median of ≥10 runs. Include in the timed region: cache assembly and re-rotation, layer 0 and the selection layer, the selective layers, final norm, and lm_head on the last token. Exclude chunk-store lookups from host memory unless you report them separately (CacheBlend hides loading behind recompute; your KV stays on GPU). The full-prefill baseline must use the same attn backend and dtype, with `use_cache=False` or the same cache handling. Python overhead of a per-layer loop is significant at small s, so report tokens computed and FLOPs next to wall time.
- **FLOPs accounting [inference]:** Per layer, the linear cost for s recomputed tokens is ≈ 2·s·(4096·(4096 + 2·1024) + 4096·4096 + 3·4096·14336) ≈ 2·s·0.218 GFLOP (q, k/v (GQA), o, and the SwiGLU MLP), so about 0.44 GFLOP per token per layer and ≈ 14 GFLOP/token for 32 layers. Attention cost is ≈ 4·s·N·4096 per layer (QKᵀ and AV over 32 heads × 128). Selective recompute makes attention O(s·N) instead of O(N²/2). Report `FLOPs_method / FLOPs_full` with the selection layer charged in full.

### Gaps
- I did not verify current PyTorch defaults for TF32 on matmul (they have changed between versions). Check `torch.backends.cuda.matmul.allow_tf32` on the pinned build.
- No source measured the SentencePiece boundary effect specifically for Mistral v0.3 chunk concatenation. It is an expected failure mode to test, not a documented finding.

## Q5. LoCoMo evaluation details and a cheaper fidelity metric

### Takeaway
LoCoMo's official F1 lowercases, strips punctuation and commas, removes "a/an/the/**and**", and **Porter-stems** tokens before token-level F1. Category 1 (multi-hop) is scored as the mean over comma-split gold sub-answers of the best-matching predicted sub-answer. Category 3 uses only the first `;`-separated gold answer. Category 5 (adversarial) is a binary check for "no information available"/"not mentioned". Use the repo's code verbatim and report categories 1-4 and 5 separately.

### Cited Findings
- **Normalization [code]:** `normalize_answer`: `s.replace(',', "")`, lower, remove punctuation, `regex.sub(r'\b(a|an|the|and)\b', ' ', text)`, whitespace collapse (evaluation.py L75-92). `f1_score` Porter-stems (`nltk.stem.PorterStemmer`) each token and computes Counter-overlap precision/recall/F1 (L126-139). — [locomo evaluation.py](https://github.com/snap-research/locomo/blob/main/task_eval/evaluation.py)
- **Per-category scoring [code]:** cat 3: `answer = answer.split(';')[0].strip()`. Cats 2, 3, 4: plain `f1_score`. Cat 1: `f1()`, which splits prediction and gold on `,` and returns `mean over gold of max over predictions of f1_score`. Cat 5: 1 if `'no information available'` or `'not mentioned'` appears in the lowercased output, else 0 (L189-224). The in-code comment reads "single-hop, temporal, open-domain eval without splitting" for 2/3/4 and "multi-hop" for 1. — [locomo evaluation.py](https://github.com/snap-research/locomo/blob/main/task_eval/evaluation.py)
- **Category meaning from prompts [code]:** cat 2 questions get the suffix `" Use DATE of CONVERSATION to answer with an approximate date."`, so 2 = temporal. Cat 5 questions get `" Select the correct answer: (a) {} (b) {}. "` with "Not mentioned in the conversation" and the stated answer in random order. `get_cat_5_answer` maps a one- or three-character reply ("a" / "(a)") back to the option text (gpt_utils.py L128-145, L243-256). — [locomo gpt_utils.py](https://github.com/snap-research/locomo/blob/main/task_eval/gpt_utils.py)
- **QA prompt [code]:** `"Based on the above context, write an answer in the form of a short phrase for the following question. Answer with exact words from the context whenever possible.\n\nQuestion: {} Short answer:"`. The cat-5 variant drops the short-phrase instruction. The RAG context is formatted as `date_time + ': ' + context`, joined by newlines. Observation chunks use `'DATE: ' + session_date_time + '\n' + 'CONVERSATION:\n' + turn`. Conversation preamble: `CONV_START_PROMPT = "Below is a conversation between two people: {} and {}. The conversation takes place over multiple days and the date of each conversation is wriiten at the beginning of the conversation.\n\n"`. — [locomo gpt_utils.py](https://github.com/snap-research/locomo/blob/main/task_eval/gpt_utils.py) L25-51, L163-195
- AgentKVShift reports "token-level F1, ROUGE-1, BLEU-1" on LoCoMo (10 conversations; multi-hop, temporal, reasoning QA) but, in the parts fetched, does not specify max new tokens or category filtering. — [AgentKVShift arXiv](https://arxiv.org/html/2607.21604) §4.1
- The dataset has 10 conversations and 1,986 questions, averaging about 16K tokens per conversation. — proposal §4.1 (local), citing [LoCoMo paper](https://arxiv.org/abs/2402.17753)

### Inferences
- **Category 5 convention [inference]:** Many later memory papers drop cat 5 because its official scoring is a substring check that a verbose model can pass by accident. With Mistral, either use the repo's (a)/(b) multiple-choice format with greedy decoding and `get_cat_5_answer`, or exclude cat 5 and say so. Report the main F1 on cats 1-4 (1,540 questions if the commonly cited split holds; verify by counting) and cat 5 accuracy separately. Since AgentKVShift is the comparison point, try to match its choice, which is unstated in the parts I read.
- **Answer length [inference]:** Mistral-Instruct tends to write full sentences, and F1 precision drops sharply because each extra token counts. Use the repo's QA prompt, greedy decoding, `max_new_tokens` ≈ 32, and stop at the first newline. Strip phrases like "The answer is". Apply the same post-processing to every method. Answer length is identical across methods only if decoding is deterministic and the KV is close, so report mean answer length per method as a sanity check.
- **Cheaper fidelity metric [inference]:** For each (prompt, method), teacher-force the **full-prefill greedy answer** (or the gold answer) after the method's assembled cache and compute (a) the mean log-likelihood of those tokens and (b) the mean per-token KL(p_full ‖ p_method) over the answer positions, plus top-1 agreement on the first token. It needs one forward pass of ~20 tokens per question, no generation and no F1 noise, and it gives a smooth curve against recompute budget. Use it to tune k/r and select operating points, then confirm with F1 at those points. KL on the first generated token alone is the cheapest version, since it only needs the prefill logits.

### Gaps
- I did not fetch the LoCoMo paper itself to confirm the official category names/numbering (the repo code shows 2 = temporal and 1 = multi-hop by comment). The per-category question counts were not verified.
- I found no source specifying AgentKVShift's LoCoMo generation settings (max tokens, cat-5 handling, prompt). That limits how directly our F1 can be compared with their 0.509 / 0.491.
