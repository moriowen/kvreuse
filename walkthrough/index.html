Prefill once, reuse anywhere

Non-prefix KV reuse for agent memory. We cache each memory chunk's KV once, move it to wherever the chunk lands in a new prompt, and measure how much answer quality each correction method buys back for how much recompute.

The problem in one picture

A memory agent retrieves a few chunks for each question and puts them before the question. Two questions about the same conversation often retrieve the same chunks in a different order. vLLM's prefix cache only matches identical leading tokens, so it stops matching right after the system prompt.

Prefix caching: only the system prompt hits. C and A were computed seconds ago but get prefilled again because they moved. Our idea: keep C's and A's KV, keyed by their tokens, and reuse it at the new position.

Why it isn't free

Error 1: position. Keys carry their position through RoPE. A chunk cached at position 2 and reused at position 810 has keys rotated for the wrong place.

Fix is exact: rotate the cached keys by the position difference. Rotations add up, so one extra rotation does it.

Error 2: missing context. A chunk cached alone never attended to the chunks now in front of it. Its KV at layers 1 to 31 is slightly wrong.

No rotation fixes this. The four methods differ in which tokens they recompute to patch it. That trade-off is the project.

Research question

Core: How much prefill can non-prefix KV reuse remove from a memory-augmented agent, and how do different ways of correcting reused KV trade answer quality against prefill cost?
Secondary: Served through unmodified vLLM, does reuse lower time to first token and raise throughput, and how often must memories repeat before it beats prefix caching?

The contribution is engineering and evaluation. The correction algorithms come from EPIC, CacheBlend and AgentKVShift. What's new is comparing all of them on one conversational memory workload under one budget formula, an independent reimplementation of AgentKVShift (it has no public code), and serving reuse through vLLM's public connector API without editing vLLM.

If you have two minutes with the professor

  1. Problem. Memory agents put retrieved chunks before each question. The same chunks come back in new orders, and vLLM's prefix cache misses them, so they get prefilled again.
  2. Idea. Cache each chunk's KV once under a hash of its tokens. When it shows up again, rotate its keys to the new position (exact) and patch the missing cross-chunk attention by recomputing a few tokens.
  3. Study. Four ways to pick those tokens (none, chunk starts, top deviating tokens, probes plus a mean shift), one shared recompute loop, one budget formula, on Mistral-7B and LoCoMo.
  4. Done. Pipeline, store, all four methods and the vLLM connector are built. The correctness gate passed on the real model with logit errors around 5e-5 against a 1e-3 tolerance.
  5. First signal. On 100 questions, uncorrected reuse drops F1 from 0.244 to 0.129, temporal questions worst, while prefill gets 2.6× faster (78.9 → 29.9 ms) after we removed a cuDNN overhead. That gap is what the correction methods are supposed to close.
  6. Next. The 16-config quality sweep and full baselines are running on PACE. Then the k-sweep for timing, the vLLM match check, and the serving benchmark.
