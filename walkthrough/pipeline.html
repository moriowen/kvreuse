One question, end to end

What happens to a single LoCoMo question, from raw conversation JSON to an F1 score. Steps 1-2 run once, offline, on a CPU node. Steps 3-7 run per question on the GPU, once per method configuration.

1

Chunk the conversation

Each LoCoMo conversation has up to ~35 sessions of dialogue. We pack whole turns from one session into chunks of about 256 tokens. A turn is never split. Every chunk starts with LoCoMo's own date header so temporal questions stay answerable.

DATE: 1:56 pm on 8 May, 2023
CONVERSATION:
Caroline said, "Hey Mel! Good to see you! How have you been?"
Melanie said, "Hey Caroline! Good to see you! I'm swamped with the kids & work..."
...

kvreuse/locomo.py · chunk_conversation()

2

Tokenize once, retrieve once, save to disk

Each chunk is tokenized on its own, one time. Then BM25 picks the top-10 chunks for every question. Both go to disk, and every experiment reads those same files. No method can win or lose because of retrieval.

data/chunks.json
per conversation: speakers, chunks with text and token ids
data/retrieval_k10.json
per question: category, gold answer, ranked chunk ids

scripts/prepare_data.py · kvreuse/retrieval.py (BM25, optional dense embeddings) · PACE job pace/prepare.sbatch

3

Build the prompt from token ids

The prompt is a concatenation of stored token ids, never re-tokenized text, because SentencePiece can merge tokens across a join. That guarantees the full-prefill reference and the reuse path see exactly the same ids. run_eval.py asserts it on every question.

[BOS][INST] system
chunk 7
chunk 2
chunk 19
…×10
question [/INST]
prefix: always at position 0, cached exactly retrieved chunks: reused, any order question: always computed fresh

With top-10 retrieval the prompt averages about 2,330 tokens (measured on the first 100 questions).

kvreuse/prompt.py · PromptBuilder (Mistral v0.3 has no system role, so the system text goes inside [INST])

4

Look up each chunk in the KV store

The store is a dict keyed by a SHA-256 hash of the chunk's token ids. On a miss, it prefills [BOS][INST] + chunk and keeps only the chunk's slice, so the chunk sits at canonical positions starting at 2. Prefilling after [BOS][INST] means the chunk's first token isn't treated as the attention sink. A hit also compares the ids, so a hash collision can't return the wrong KV.

Stored per chunk: keys (after RoPE, at canonical positions) and values, for all 32 layers, 8 KV heads, 128 dims. About 128 KiB per token in bf16.

kvreuse/store.py · ChunkStore.chunk(), ChunkStore.prefix()

5

Assemble the cache and re-rotate keys

Each chunk lands somewhere new. Its keys get one extra RoPE rotation by delta = new_start − canonical_start. Values are not rotated. The rotation is computed in fp32 and cast back once, always from the stored canonical position, so rounding error doesn't build up.

The output is a reused cache K0, V0 covering the whole prompt, plus a Layout that records where the prefix, each chunk and the question sit. Question slots are left as zeros since they're always computed.

kvreuse/store.py · assemble() · kvreuse/rope.py · shift_keys()

6

Selective prefill: the one loop every method shares

We step through Mistral's 32 decoder layers by hand. At each layer only a set S of tokens is recomputed. Everything else is read from the reused cache. A method is just a Plan object that picks S.

S = plan.initial_set(layout)          # always includes the whole question
h = embed(ids[S])
for layer in 0..31:
    q, k, v = qkv(layer, h, positions[S])
    K = K0[layer].clone();  K[S] = k     # write fresh KV first, so
    V = V0[layer].clone();  V[S] = v     #   recomputed tokens see each other
    keep = plan.on_layer(layer, S, K, V, K0, V0)   # may shrink S, may adjust K/V
    if keep: S, h, q = keep, h[keep], q[keep]
    h = attention(q over ALL K, V, mask kv_pos <= q_pos) + MLP
logits = lm_head(norm(h[last]))
Why hand-written instead of model(...): the queries are a scattered set of positions, not a contiguous block. HF's SDPA path without an explicit mask assumes contiguous queries and crops K/V, which would be silently wrong. So every attention call passes an explicit kv_pos ≤ q_pos mask. FlashAttention-2 can't express that mask, so it isn't used for selective recompute.

S can only shrink with depth: a token recomputed at layer l needs its fresh hidden state from layer l−1. The full-prefill reference runs through this same code, so kernel differences never show up as reuse error.

kvreuse/forward.py · selective_prefill(), full_prefill() · kvreuse/methods.py · the plans

7

Decode, score, log

Greedy decoding for up to 32 tokens on top of the (possibly approximate) cache. Keep the first line of the answer, score it with LoCoMo's own F1 (ported scorer: stemming, article removal, category-specific rules). Category 5 (adversarial) is scored separately; the headline number is categories 1-4.

Per question, one JSON line: prediction, F1, prompt length, prefill ms, recompute budget, and with --kl the KL divergence and top-1 agreement of the first answer token against full prefill. Per run, a summary file with the full config (model id, GPU, torch version, k, budget, seed).

kvreuse/forward.py · greedy_decode() · kvreuse/metrics.py · scripts/run_eval.py → results/<name>.jsonl + .summary.json

8

Compare runs

All runs over the same questions are joined and compared against full. Differences get paired bootstrap 95% CIs over questions, plus a conversation-level bootstrap, because LoCoMo has only 10 conversations and questions within one conversation aren't independent.

scripts/analyze.py · kvreuse/metrics.py · paired_bootstrap()

The served path (vLLM, method 1 only)

Same idea, inside an unmodified vLLM through its KV-connector plugin interface. vLLM asks the connector "how many leading tokens of this prompt can you supply?" We answer with the re-rotated chunk KV, and vLLM only computes the rest.

Export
Build the store offline from the Transformers path, in vLLM's packed layout. ~2.8 GB for one conversation (conv-26).
scripts/export_store.py
Match
Walk the prompt: exact prefix first, then find each chunk by its first 8 tokens and confirm the full ids. Any order works.
connector_logic.py · StoreIndex.match
Align
vLLM counts hits in 16-token blocks, so round down. vLLM computes the question plus at most 15 tail tokens.
connector_logic.py · matched_tokens
Load
Re-rotate K in the packed layout and write into vLLM's paged KV cache at the right slots.
vllm_connector.py · ChunkReuseConnector

Methods 2-4 need recompute inside the prefix at every layer, which would mean changing vLLM's scheduler. That's out of scope, so they stay in Transformers. Prefix caching must be off when the connector runs, otherwise vLLM would register the approximate KV under exact token hashes.
