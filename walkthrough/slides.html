Hi Professor. We're Group 7, and our project is about making memory-augmented LLM agents cheaper to serve. The idea in one line: compute each memory's KV cache once, then reuse it wherever that memory shows up in a prompt, even when it isn't at the start. Start with what an agent memory is. An LLM chat agent that talks with someone over months can't fit the whole history in its context. So it saves the conversation as memory entries. When a new question comes in, a retriever picks the few most relevant entries, and the agent pastes them into the prompt in front of the question. Systems like MemGPT and A-Mem work this way. The dataset we use, LoCoMo, has ten very long multi-session conversations and about two thousand questions about them.

To see where the cost is, recall how an LLM answers. There are two phases. Prefill reads the entire prompt in one parallel pass through all the layers. That pass produces the KV cache, which I'll explain next, and the first token of the answer. Then decode writes the answer one token at a time; each step just reads the cache and adds one entry. Prefill cost grows with prompt length, and the user waits through all of it before seeing anything. With a long retrieved prompt, that wait is mostly prefill.

Background 3 · the KV cache

Prefill leaves behind one K and V per token, per layer

Layer 32

Layer 1

Prompt tokens →

One cell = a key vector and a value vector for one token at one layer. Decode reads these instead of recomputing the prompt.

Mistral-7B: 32 layers × 8 KV heads × 128 dims × (K and V) × 2 bytes = 128 KB per token. A 2.3K-token prompt carries about 300 MB of KV.

TWO FACTS WE NEED LATER

A token's KV encodes where it sits in the prompt.

A token's KV depends on every token before it.

The KV cache is what prefill leaves behind: for every prompt token and every layer, a key vector and a value vector. Picture this grid: tokens across, layers up. Each cell is one token at one layer. For Mistral-7B, that's 128 kilobytes per token. Two facts about these cells matter for everything that follows. First, a token's key encodes its position in the prompt. Second, because of attention, a token's KV at every layer above the first depends on all the tokens before it.

Serving engines already avoid some of this work. It's exact, because the reused text has the same text in front of it. Keep that condition in mind: it's what breaks for agent memory.

Each question retrieves memories in a new mix and order. vLLM only reuses KV when two prompts start with identical tokens, so its prefix cache stops matching right after the system prompt.

Prefill grows with prompt length and dominates time to first token. Over a long conversation, the same memories get prefilled many times.

Before an LLM writes its first token, it runs prefill: one pass over the prompt that computes a key and value vector for every token at every layer. That's the KV cache, and for long prompts it dominates time to first token. Memory-augmented agents retrieve entries from long-term memory and put them in front of every question. Here, question 1 pulls memories A, B, C. Question 2 pulls C, A, D. A and C were already computed, but vLLM's prefix caching only matches identical starting tokens, so after the system prompt everything is prefilled from scratch again.

Problem statement

Memory agents keep retrieving the same entries in new combinations and orders. vLLM prefills them from scratch every time, because it only reuses identical prefixes. We want to reuse a memory's KV wherever it lands in the prompt.

RESEARCH QUESTION

How much prefill can non-prefix KV reuse remove from a memory agent, and how do different ways of correcting reused KV trade answer quality against prefill cost?

SECONDARY QUESTION

Served through an unmodified vLLM, does reuse lower time to first token and raise throughput? How often must memories repeat before it beats prefix caching?

So here's the problem statement. Memory agents keep retrieving the same entries in new combinations and orders, and vLLM prefills them from scratch each time because it only reuses identical prefixes. We want to reuse a memory's KV wherever it lands in the prompt. The research question: how much prefill can that remove, and how do different ways of correcting the reused KV trade answer quality against prefill cost? The secondary question is about serving: through an unmodified vLLM, does it actually lower time to first token and raise throughput, and how often do memories need to repeat before it beats plain prefix caching?

Our approach

Prefill each memory once, reuse its KV at any position

01

Chunk

Whole dialogue turns from one session, packed to about 256 tokens

02

Prefill alone

First time it is retrieved; store its KV under a hash of its tokens

03

Load

Later prompts fetch the stored KV for each retrieved chunk

04

Re-rotate

Shift the cached keys to their new position with RoPE

05

Correct

Recompute a few tokens; the question is always computed fresh

Prefix caching needs the same prompt start. We only need the same chunk, anywhere in the prompt.

Our approach: treat each memory entry as a chunk. The first time a chunk is retrieved we prefill it on its own and store its KV under a hash of its tokens. Later prompts that contain the chunk load that KV, re-rotate the keys to the new position, and then apply a correction. The question at the end is always computed fresh. So instead of needing the same prompt prefix, we only need the same chunk.

The catch

Reused KV is wrong in two ways

ERROR 1 · POSITION

The chunk now sits somewhere else

Keys encode where a token sits. Rotary embeddings let us re-rotate cached keys to the new position.

Fix is exact

ERROR 2 · CONTEXT

The chunk never saw its new neighbours

Cached alone, it never attended to the memories now in front of it. No rotation fixes that.

Fix is approximate: recompute some tokens

Which tokens to recompute is the question our project studies.

Reusing KV at a new position isn't exact, for two reasons. First, position: a token's key depends on where it sits. With rotary position embeddings we can fix that exactly by re-rotating the cached keys. Second, context: a chunk cached on its own never attended to the memories now placed before it, and no rotation fixes that. The error is usually small, because tokens mostly attend within their own chunk, but closing it means recomputing some tokens. Which tokens is the question we study.

These are the four corrections we compare, and they differ only in which tokens get recomputed. Method 1 recomputes nothing; it's the baseline. EPIC assumes the error lives at chunk boundaries, so it recomputes the first few tokens of each chunk. CacheBlend assumes the error is sparse and can be anywhere: it picks the tokens that deviate most at an early layer. AgentKVShift assumes most of a chunk's error is one shared offset: it recomputes a few probe tokens, estimates the mean shift and adds it to everything else. AgentKVShift is our main comparison point. It has no public code, so ours is an independent reimplementation, and no one has compared all of these on one conversational-memory workload under one cost accounting.

Why the start?

Cached alone, a chunk's first tokens act as an attention sink: later tokens dump attention there. Mid-prompt, that is wrong.

How it works

  1. Reuse every chunk, re-rotated.
  2. Recompute each chunk's first k tokens at every layer.
  3. Compute the question.

No selection step, so it is simple and cheap. AgentKVShift never compared against it; we will.

Method 2 is EPIC. Its observation: when a chunk is cached on its own, its first tokens become an attention sink, a place where attention piles up. Once the chunk sits in the middle of a prompt, that's wrong. So EPIC recomputes the first few tokens of every chunk, at every layer: the blue columns. Everything else is reused. It's simple and needs no selection step, costing a fixed 16 to 32 tokens per chunk. AgentKVShift's paper never compared against it, so we will.

Method 3 is CacheBlend. It assumes the error is sparse but could be anywhere, so it measures. It runs the first two layers fresh for every token, then at the dashed line compares the fresh values with the reused ones and picks the 15 percent of tokens that drifted most. Only those get recomputed in the layers above. Note that the measurement itself costs two full layers, and our budget counts that. It reported big TTFT wins on RAG, but on LoCoMo the AgentKVShift paper reports it losing a lot of quality, 0.29 versus 0.51 F1, which is one reason to test it ourselves.

Our main comparison. Reports 0.491 vs 0.509 F1 on LoCoMo at a 10% budget. No public code, so ours is a reimplementation.

Method 4 is AgentKVShift, our main comparison point. Its analysis found that most of a chunk's error is one shared offset, the whole chunk drifting the same way. So instead of recomputing many tokens, it recomputes a few probes per chunk, measures how far they moved, and adds that average shift to every other token in the chunk. That's the darker orange: reused, but corrected. It reports 0.491 F1 against 0.509 for full recompute on LoCoMo at a 10 percent budget. It has no public code, so ours is an independent reimplementation.

Every configuration reads the same saved retrievals. The connector serves method 1 only: methods 2 to 4 recompute tokens inside the prefix at every layer, which would need vLLM scheduler changes, and editing vLLM is out of scope.

Two tracks. The core is C1 and C2 in plain Transformers: a memory pipeline that chunks LoCoMo and saves retrievals to disk, so retrieval can never explain a difference between methods, and a reuse engine with the KV store, re-rotation, and one recompute loop that all four methods plug into. That answers the research question by itself. The second track serves reuse through an unmodified vLLM using its KV-connector plugin interface, driven by a synthetic workload where we control how often memories repeat. vLLM can only serve method 1 that way; the others would need scheduler changes.
